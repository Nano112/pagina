# A blog, and where to put one — design

Date: 2026-08-20. Status: from the user's brief — a friend wants a blog, and the hosting choices need
writing down.

## The fact that decides the hosting question

**Publishing renders in the browser.** The editor loads `@pagina/core`, renders every page and every
figure client-side, and POSTs the result. A backend stores bytes and serves them; it does not render.

So an editing backend needs no Node, no rendering, and no build step at request time. That is why a
Cloudflare Worker over R2 is a real option rather than a stretch: implement the HTTP contract, keep
the folder in object storage, serve `.rendered/` as files. The same reasoning rules out the opposite
idea — rendering at the edge on request — which pagina has never needed and should not start needing.

One thing does need Node: **social cards**, because resvg is native. Cards are generated by `build`,
not by `publish`. A site published from the browser keeps whatever cards its last build produced, and
that is worth stating plainly rather than discovering.

## Five ways to run a pagina site

| | Editing | Needs | Suits |
|---|---|---|---|
| **1. Static, edited by commit** | git | a static host | one author who likes git |
| **2. Static + git-backed editor** | the editor, writing commits | a token | a blog with no infrastructure |
| **3. Static + edge functions** | the editor, writing to object storage | Worker + R2 (or equivalent) | a blog whose author will not touch git |
| **4. Node host** | the editor, against a server | a server | an existing Node application |
| **5. Framework host** | the editor, inside the app | Laravel, Rails, Django… | docs inside a product |

1, 4 and 5 exist and are documented. **2 and 3 do not exist**, and 2 is the one a blog most wants:
commits are the storage, history and attribution come free, and there is nothing to pay for or
operate. 3 is the answer when the author should never see a repository.

Both are the same shape — an `ArticleBackend` over the documented HTTP contract — which is the point
of having written that contract down.

## A blog is a form, not a fork

`form` is validated as `"docs"` and nothing else. Adding `"blog"` changes what a build does with the
same folder, rather than adding a second kind of project:

- **The index is generated, not written.** Docs get their order from `nav`; a blog gets it from
  dates, newest first. `nav` becomes optional for a blog and, when present, means a fixed set of
  standalone pages (about, colophon) rather than the reading order.
- **A page gains `date`** — required for a post, and the thing everything else sorts by. `draft: true`
  keeps a post out of the index, the feed and the sitemap while remaining buildable.
- **prev/next become older/newer**, which is what the arrows mean on a blog and the opposite of what
  they mean in docs.
- **A feed.** `feed.xml` (Atom), because a blog without one is a blog that cannot be followed. Absolute
  URLs, so it needs `site_url` — the same input the canonical already needs.
- Tags already exist in the format; a blog gives them somewhere to land.

Reading time, covers, descriptions, search, social cards, `llms.txt`, bundles and the editor all work
unchanged. That is the argument for a form rather than a fork: a blog is a docs site that sorts by
date and can be subscribed to.

## Deliberately not now

Comments, pagination, related posts, per-tag pages, and multi-author bylines beyond the one `author`
field. Each is a real feature and none is needed to publish a first post. Pagination in particular is
worth resisting until an index is long enough to hurt.

## Verification

The blog form gets the tests the docs form has, plus the ones only it can fail: index order against
mixed and missing dates, a draft absent from index, feed and sitemap while still building, the feed
validating, older/newer pointing the way a reader expects, and `nav` meaning standalone pages rather
than order. Then write three posts and read them.

The hosting work is verified by running it: a Worker under `wrangler dev` against local object
storage, driven by the editor — write, conflict, publish, read back — rather than a snippet that has
never been executed.
